    Evidence for INCORRECT / WEAK findings¶

    E1 arrays/array_tests.fire INCORRECT. println(numbers) (numbers: int32[] = [10,20,30,40,50]) and println(names) are expected to print [...]. That literal comes from flir/lowering.py::_array_to_string fallback ConstStr("[...]") used when the array length is unknown. Probe: a: int32[]=[10,20,30]; println(a) -> [...]; b: int32[3]=[1,2,3]; println(b) -> [...] (even statically sized!), but println(b as string) -> [1, 2, 3] and array_to_string.fire expects [1, 2, 3] for the same data. So println(array) silently degrades to a placeholder while as string works: the EXPECT block blessed a compiler inconsistency/placeholder. Suggest: fix compiler or delete the println(array) lines; this test is the only place [...] appears in tests/. The rest of the file is redundant.

    E2 control_flow_braceless_if_at_eof.fire INCORRECT (pins likely-bug). The source ends with if (b) and no body and compiles successfully (probe: exit 0) and runs. A dangling if with no statement is malformed; the test was written to cover a parser fallback branch (_parse_braceless_body returning None at EOF) and blesses it as valid. Suggest: make the parser emit a diagnostic and move this to tests/sources/invalid/ (compile-fail with //~ ERROR), or at minimum state in the header that it is a pinned leniency. Mark with owner decision.

    E3 Trailing-blank-line blindness. strings_index_of_substring: println(s.substring(10,2)) prints "" as the final line; strings_upper_lower: last two printlns print "" . normalize_output() strips them so e.g. a regression that printed "x" is caught but one that printed " " or nothing is not, and an off-by-one that returns the empty string vs nothing cannot be distinguished. Fix: wrap in markers (println("[" + s.substring(10,2) + "]") -> []) or reorder so the empty case is not last. Also add a one-line header note that substring clamps out-of-range bounds (negative start -> 0, end>len -> len, start>end -> "") since this is pinned but undocumented (only the changelog mentions the methods).

    E4 strings_comparison WEAK. Only literal-vs-literal equal ("apple"=="apple", which may be interned/pointer-equal), and one unequal same-length-class case. Missing: different lengths with common prefix ("app" vs "apple"), equal-length-different-content ("abc" vs "abd"), empty string, and equal strings built at runtime ("ap"+"ple" vs "apple") which would catch a pointer-compare regression. I probed all of these: they currently work (false,true,false,true,true,true,false), so the replacement is just those lines.

    E5 strings_unicode WEAK. Only round-trips bytes through println. Probe: "café".length() == 5 (byte count, not 4 chars), so length/indexOf/for-in semantics on non-ASCII are byte-based and undocumented; test pins none of it (good: not wrongly pinned, but also would not catch a regression in length/slicing on multibyte input). Suggest adding .length() expectation only once the owner decides the intended semantics.

    E6 arrays_typed WEAK. int8 array reads only [0] and length; int64 reads only [1]; f64 only [1]; bool [0],[1]. A wrong element stride for int8/int16/uint8 (1-byte elements) would be invisible at index 0. Read the last element of each typed array (and at least 3 elements of the int8 one); other widths (uint8/16/32/64, int16, char) absent.

    E7 for_in_and_match_temporaries WEAK/misfiled. Bundles match-on-call-result and sized-array-declaration paths (not control flow). uninitialized: int32[4] reads only [0]: zero-initialization of a sized array is only asserted for one element of one array in the whole suite (array_to_string's int32[0] has no elements); a fresh stack frame may already be zero there. Suggest reading all 4 elements, and after dirtying the stack with a prior function call. Also relocate the match/array-decl parts to match/ and arrays/.

    stress_*: manifest (tests/TEST_MANIFEST.md lines 659-665) describes these as "stress", "heavy", "repeated" tests; none loops more than 10 times or allocates more than a few objects. There is NO real performance/stress test in the directory. Runtimes are all <2 s including wine start-up, so nothing is slow; nothing stresses either. Suggested real stress tests: recursion depth ~1e5 (stack limit behavior), a 1e6-iteration loop with string concatenation/drop (leak/allocator), a large (e.g. 1e5-element) array fill/sum.

    Compiler bugs / doc mismatches discovered (minimal repros; all verified by me under wine)¶

    B1 println(array) prints "[...]" (see E1): a: int32[3] = [1,2,3]; println(a); // prints [...] ; println(a as string) prints [1, 2, 3]

    B2 Out-of-range array index is unchecked, reads garbage; docs/reference/arrays.md says it "will cause a runtime error": a: int32[] = [1,2,3]; i: int32 = 5; println(a[i]); println("after"); // prints 6029362 then "after", exit 0 No test anywhere pins OOB behavior; stress_array_bounds does not either.

    B3 Signed integer overflow wraps silently; docs/reference/error_handling.md says it "traps at runtime rather than silently wrapping": a: int32 = 2147483647; b: int32 = a + 1; println(b); // prints -2147483648, exit 0 (stress_integer_overflow never overflows, so the doc/impl mismatch is not caught. edge_cases/edge_cases_overflow_underflow.fire is labelled "behavior may vary"; outside my slice.)

    B4 ICE returning an array literal from an int32[] function (also noted in for_in_and_match_temporaries header, but NOT captured by any known-issue test; note tests/sources/known_issues/ does not exist, only invalid/known_issues/): fn mk() -> int32[] { return [1,2,3]; } x: int32[] = mk(); println(x.length()); -> FIR verifier dump (FIRV-T4 'int32[3]' vs declared 'int32[]'), no binary. (functions_array_return.fire only returns a param.)

    B5 if (b) with no body at EOF compiles (see E2).

    B6 String literal with embedded NUL truncates: r: string = "a\rb\0c"; println(r.length()); -> 3 (expected 5): strings are NUL-terminated C-style; string_escape_edge_cases.fire header claims \0 is handled but no test exercises it. Likely a known limitation; worth a documented note or a test.
