    S3 audit: types / conversions / operators / edge_cases / identifiers / io (53 files)¶

    Method: every file compiled + run in a private temp dir (wine) with my own runner; all 53 outputs MATCH their EXPECT blocks, so no test is stale. Numerics re-derived with a Python oracle (two's-complement wrap, struct float32 rounding, printf %f for float64). All EXPECT values are arithmetically right under the compiler's actual semantics; the INCORRECT verdicts below are about pinning behavior that contradicts the docs or is undefined/undocumented. Docs facts used: type_system.md L141-153 and error_handling.md L31-38 say fixed-width int overflow TRAPS at runtime (compile error if constant-detectable). Float printing is printf "%f" (6 digits; stated in special_types/float128_ops.fire). Harness normalisation (tests/harness/expectations.py:20) rstrips every line and strips trailing blank lines.

    Detailed evidence¶

    #1 INCORRECT: wraparound pinned where docs mandate a trap¶

    types_int8.fire, types_uint8.fire, edge_cases_overflow_underflow.fire expect 127i8 + 1i8 = -128, -128i8 - 1i8 = 127, 255u8 + 1u8 = 0. docs/reference/type_system.md L141-153 and error_handling.md L31-38: "arithmetic ... that exceeds the representable range will throw an error at runtime ... constant expressions are compile-time errors". The compiler wraps silently (also int32: 2147483647 + 1 -> -2147483648, 2 ** 31 -> -2147483648, uint8 0-1 -> 255; verified by probe). Either the compiler is wrong (and these must move to tests/sources/known_issues/ or become an expected-trap test), or the docs are stale; in both cases blessing wrap silently is wrong. Owner decision needed; stress_integer_overflow.fire (performance/, out of my slice) pins the same wrap. Suggested: delete the overflow lines from the three files; add one test that states the decided semantics (trap test, or // note + wrap test if docs get changed).

    #2 builtin_conversions.fire¶

    toChar("65") expects 6; toChar(66) (other file) expects B. TEST_MANIFEST documents "toChar on a string takes its first character's code point". No reference doc defines these builtins; parser/type_system.py L873 still special-cases them. Not wrong per se but unspecified and self-inconsistent; recommend confirming the builtins are supported, otherwise mark known-legacy. If kept, drop the toChar("65") line.

    #3 int_float_cast_matrix.fire¶

    f1 as int8 (200.9) -> -56, as int16 -> 200: out-of-range float->narrow-int is UB in C, docs only say "may lose precision or truncate". Probe results (all pinned nowhere): NaN as int32 = 0, inf as int32 = 0, inf as int64 = -9223372036854775808, 300.5 as uint8 = 44, -1.5 as uint8 = 255, -1.0 as uint64 = 18446744073709551615, 2147483648.0 as int32 = -2147483648, 1e10 as int32 = 1410065408. Keep only in-range cases (the uint64 >2^63 lines are good and verified: float32(1.8e19) = 18000000404716257280 exact), or document the semantics first.

    #4 conversions_regression_uint64_to_float.fire (WEAK + real bug)¶

    Header says the odd value (2^63+1) checks "the halving step must keep the sticky bit". 2^63+1 rounds to 2^63 with or without a sticky bit, so the case cannot fail. A value that does need it: 9223372036854776833u64 (= 2^63+1025). Correct float64: 9223372036854777856.000000 (python float(2**63+1025)). Compiler prints 9223372036854775808.000000: WRONG (see bugs). Replacement lines: println(9223372036854776833u64 as float64); expect 9223372036854777856.000000 (will fail until fixed => known_issues convention or fix compiler first).

    #5 conversions_float_precision.fire¶

    Header: "Float64 to float32 (precision loss)". Output shows no loss: 3.141593 / 3.141593 (6-digit %f). Test cannot detect a no-op cast. Replacement: println((precise as float32) as float64 == precise) expect false; println((0.1f as float64) == 0.1) expect false (I verified the latter is false today), println((16777217.0 as float32) as float64) expect 16777216.000000.

    #6 float ** fractional exponent (see bugs); operators_arithmetic.fire should add println(2.0 ** 0.5) -> 1.414214, 9.0 ** 0.5 -> 3.000000.¶

    WEAK summary of printing¶

    Every float assertion goes through %f (6 decimals) so float32 vs float64 storage, subnormals, rounding mode and NaN/inf formatting (inf/-inf/nan do print as inf, -inf, nan; -0.0 prints -0.000000) are essentially untested in this slice; no test in the slice covers NaN, inf, float overflow (3.4e38f32*10 -> inf works), or the documented type_system.md NaN/Infinity examples.

    Compiler bugs discovered (all reproduced in private dir)¶

    1. NaN comparisons are wrong (IEEE says all false except !=): z: float64 = 0.0; n: float64 = z / z; println(n == n) -> true (expected false) println(n == 1.0) -> true (false); n < 1.0 -> true (false); n <= 1.0 -> true (false); n > 1.0, n >= 1.0 false (ok) same for float32. Docs: "Floating point operations follow IEEE 754 semantics". Looks like ucomisd with unordered (ZF=PF=CF=1) not checked for PF.
    2. Float ** ignores fractional exponent: println(2.0 ** 0.5) -> 1.000000 (1.414214); 9.0 ** 0.5 -> 1.000000 (3); 2.0 ** 1.5 -> 2.000000 (2.828427); 10.0 ** 2.5 -> 100.000000 (316.227766). Integer exponents are fine. Exponent is truncated.
    3. uint64 -> float64 loses the sticky bit: println(9223372036854776833u64 as float64) -> 9223372036854775808.000000, correct 9223372036854777856.000000. (2^63+1025; not rounded up; values < 2^63 and exact halves are fine.)
    4. Integer overflow wraps instead of trapping (docs contradiction, see #1).
    5. 2 ** -1 (int) prints 1 (undocumented; should likely be error or 0); int 5 / z with z == 0 raises a raw hardware divide-by-zero (wine: "Unhandled division by zero"), not the documented firescript runtime error. Not covered by any test in my slice.
    6. Float->int casts of out-of-range/NaN/inf values are silent and inconsistent between widths (see #3 list) - spec gap more than bug.

    Could not verify: native Windows behavior (only wine); the harness's own run of these tests (not run per instructions; my private runner reproduced all 53 EXPECT blocks); the redundancy claims for edge_cases_* vs scoping/functions/arrays tests rest on grep + reading, not on mutation testing.
