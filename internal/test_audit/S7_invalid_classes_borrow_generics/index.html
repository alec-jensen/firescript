    S7 audit: tests/sources/invalid/{classes,borrow,generics} (72 files, no helpers)¶

    Method: read every file; ran the real compiler (--check --message-format json) on each; wrote /scratchpad/audit/cmp.py to confirm annotations == actual diagnostics (all 72 currently pass, so no stale columns); wrote ~30 scratch programs in /tmp/.../scratchpad/audit/t/ (a1..f4) to separate primary errors from cascades and probe for missed diagnostics. Parser facts used as redundancy evidence: firescript/parser/declarations.py lines 140/188/194 (receiver/param parsing shared by methods AND constructors), 1069 (static ctor), 1086 (')' after params), 1109 ('{' body); expressions.py:247 (single site for "'(' after constructor type").

    IMPORTANT STRUCTURAL FACTS * Any parse error stops the pipeline before semantic analysis. So every file that mixes a parse error with semantic mistakes silently hides the semantic ones (see class_errors, generics_errors). * Many tests annotate CASCADE diagnostics (e.g. "Variable 'this' not defined", "Function 'Pair' is not defined", "Variable 'identity' not defined" where the name IS defined). These lock incidental error-recovery behaviour into the test; any parser-recovery improvement breaks them.

    DETAILED EVIDENCE (INCORRECT / WEAK)¶

    D1 classes/class_errors.fire (INCORRECT) Intended: undefined class, unknown field, field type mismatch, unknown method, duplicate class, duplicate field, class name used as variable, uninitialized instance. Actual annotated diagnostics (10): - l.5 UndefinedClass obj; : old C-style declaration syntax; the two PARSE-0010 "Expected assignment, function call..." are not an undefined-class error. - l.16/22/28/63 p: Point; : declaration without initializer -> PARSE-0010 "Expected '=' in variable declaration" (variables.md: declarations without initializer unsupported). The intended field/method errors are never reached. - l.17/23/29 PARSE-0003 "Variable 'p' not defined": pure cascade of the failed declaration. - l.64 PARSE-0012 "Function 'println' is not defined": println is not imported (incidental), not the intended obj.required problem. - l.38-44 duplicate class, l.47-50 duplicate field, l.54 Point: int32 = 5 : NO diagnostic, because parse errors suppress semantic analysis. In isolation (scratch a4) the compiler ALSO reports nothing for them (compiler bug B1). Fix: delete the file (every legitimate rule is covered elsewhere: unknown field = field_access_errors, unknown method = unknown_instance_method) and add real tests for duplicate class/field once B1 is fixed (known_issues).

    D2 generics/generics_errors.fire (INCORRECT + WEAK; 6 annotations) - l.5 T x;: old syntax; PARSE-0010 x2 are not "undefined type parameter". - l.15 x: int32 = identity<string>(42): comment says "expects string but got int" (argument mismatch). The compiler does NOT check the argument (scratch c4/c8: identity<string>(42) and identity<int32>("s") compile clean). The annotated SEM-0002 comes only from declared-type int32 vs result string. Test passes for the wrong reason and would keep passing if the arg check were never written. - l.19-24 add<T: Numeric> with undefined constraint Numeric, then add<string>(..): unannotated, NO diagnostic even in isolation (c5): undefined constraint and violating call both silently accepted (compiler bug B4). - l.29 identity(5); valid program, comment "May require explicit type parameter" is wrong. - l.34 identity<int32,string>(5) SEM-0010 type-arg count: the only correct, unique case (no other file tests generic function type-arg count). Move it to its own file. - l.43-44 box: Box<int32>; no initializer -> PARSE-0010; l.44 PARSE-0003 "box not defined" is a cascade; intended "generic class field type mismatch" untested (and b.value = "s" is undetected anyway, B2).

    D3 Malformed nested/unclosed type-argument tests using obsolete name-first syntax (INCORRECT) generic_class_nested_unclosed_type_args.l.14 Pair<p: Pair<int32,int32 int32> = Pair(...), nested_generic_missing_close_errors.l.14 Pair<Pair<int32, int32, p: string;, generic_declaration_errors.l.24/28 Pair<c: Pair<...> = good; These are leftovers from an older Pair<..> name declaration order. Under current name: Type syntax the line is parsed as an expression statement starting with Pair <, so the first annotation is PARSE-0010 "Expected assignment, function call, or method call" @col 1/5 (statement dispatch), not "missing '>'". generic_declaration_errors l.24/28 additionally yield FS-SEM-0002 "Expected Pair, got Pair" / "Expected int32, got Pair" which are nonsense type-mismatch cascades. The properly-formed variants work and give a sane primary error (scratch c1: p: Pair<Pair<int32,int32, int32> = Pair(Pair(1,2),3); -> PARSE-0010 "Expected '>' to close generic type arguments" @35 + cascade PARSE-0012; c2 likewise). Rewrite these three files with the current syntax (and then they collapse into generic_class_unclosed_type_args).

    D4 generics/generic_class_field_access_unknown.fire l.18 (INCORRECT: locks compiler bug) b: Box<int32> = new Box<int32>(5); with fn Box(value: T) defined is rejected: "No constructor defined for type 'Box'" (also for copyable class, and with &mut this: b2,b3). Same program with Box<int32>(5) compiles (b1). new Generic<T>(...) is undocumented/untested anywhere valid (grep docs/examples/tests: no hit), so the rejection is a bug or an unimplemented form, not an intentional rule. The test demands it.

    D5 borrow/loop_move_errors.fire, for_in_move_errors.fire (WEAK) while(..){ consume(a); } with a declared outside the loop: the second iteration uses the moved value, yet the compiler reports nothing at the call site (scratch a1: while loop, no later use -> zero diagnostics). The tests only demand the use AFTER the loop ("may have been moved on another control-flow path"). Either (a) the in-loop move should be an error and the tests are missing it, or (b) it is intentionally allowed; docs/reference/memory_management.md l.136 only says "Values used across iterations drop after loop", so the intent is unspecified. At minimum a spec decision + test is needed. Same for for-in (for_in_move_errors l.13).

    D6 Cascade-locked annotations (WEAK, systemic) FS-PARSE-0003 "Variable 'this' not defined" after a failed method/ctor parameter list: class_constructor_syntax_errors (6), constructor_param_syntax_errors (7), class_def_syntax_errors (1), constructor_amp_not_this, constructor_param_array_unsupported (2), constructor_param_bad_type (2). FS-PARSE-0012 "Function 'Pair' is not defined" etc. after a failed generic declaration: generic_class_type_arg_errors, generic_class_nested_type_arg_errors, generic_class_unclosed_type_args, generic_class_nested_unclosed_type_args. FS-PARSE-0003 "Variable 'identity'/'Box' not defined" where the name IS defined: generic_call_errors (4), generic_func_empty_type_args (1). FS-PARSE-0003 "Variable 'x' not defined" for params after a failed fn header: generic_def_syntax_errors (4). FS-PARSE-0010 "Expected initializer expression" duplicates: new_missing_paren, new_constructor_syntax_errors, new_constructor_empty_type_args, type_member_access_errors. Duplicate diagnostics for one fault: unknown new type reports PARSE-0012 AND SEM-0010 at the same column (class_new_constructor_errors l.19-20, new_constructor_syntax_errors l.14-15, new_unknown_type l.5-7).

    COMPILER BUGS / ODDITIES DISCOVERED (minimal repros; scratch files in .../scratchpad/audit/t/)¶

    B1 Duplicate class / duplicate field / class name shadowed by variable produce no diagnostic (a4): class A { x: int32; } class A { y: int32; } class B { x: int32; x: int32; } fn f()->void{ A: int32 = 5; } (the second A silently wins: A() later reports "expected 1 args, got 0" referencing the wrong class) B2 Field assignment/return type mismatch not detected (d1/d2): p: Point = Point(1,2); p.x = "string"; // no error fn get(&this)->string{ return this.x; } // x:int32, no error B3 Explicit/inferred generic call argument type not checked (c4, c8): fn identity(v:T)->T{return v;} x: string = identity(42); a: int32 = identity("s"); // no error B4 Undefined constraint name accepted; violation not reported (c5): fn add(a:T,b:T)->T{return a+b;} add("a","b"); B5 Wrong number of type args on generic class accepted (f3): a: Box = Box(1); // no error B6 new GenericClass<int32>(5) rejected with "No constructor defined for type 'Box'" although constructor exists; Box<int32>(5) accepted (b1/b2/b3). Valid program rejected or undocumented form (see D4). B7 Borrow checker holes (e1,e4,f1,d4): storing &text param into this.text; assigning/mutating through &w param (w.text = "z"); calling &mut this method (c.inc()) on a &c param; s = "x" on &s: string -- all accepted although memory_management.md l.59/78 say borrows are read-only and non-retainable. B8 Move inside loop body not diagnosed (a1/D5). B9 Unknown base class class C from Missing and cyclic inheritance accepted (e6). B10 Misleading cascade diagnostics: after a failed generic call/decl the compiler says "Variable 'identity'/'Box'/'Pair' not defined" or "Function 'Pair' is not defined" for names that ARE defined; after failed params this "not defined". B11 class NoCtor{x:int32;}: NoCtor() is accepted (implicit field constructor, "expected 1 args") but new NoCtor(5) -> "No constructor defined" (a6; class_static_method_errors.l.15 relies on Tool() with no ctor being legal). classes.md documents neither implicit constructors nor this asymmetry. B12 Methods without a receiver (fn add(a:int32) using this.value) and receiver-less constructors compile and are treated as instance methods; classes.md says receivers are required and static needs static fn. A large part of the slice (instance_method_, super_call_, constructor_call_, field_access_) is written in this receiver-less style, i.e. relies on undocumented behaviour. (static fn + this does error: b6.) B13 Re-assigning a moved owned variable (x = "again" after consume(x)) is reported as use-after-move at the assignment (f4); spec silent. B14 Unknown declared type reports PARSE-0010 "Expected type" + PARSE-0003 "Variable 'Undefined' not defined" (c7) rather than an undefined-type diagnostic.

    NOT VERIFIED: whether B7/B8/B13 are intentional design (docs are ambiguous; memory_management.md marks borrow rules IMPLEMENTED); whether instance-method statement vs initializer contexts take different semantic paths (instance_method_arg_count/type/unknown marked redundant on message equality only); error CODE choice (PARSE-0012 for "Array parameters not supported", SEM-0010 for nearly everything) was not judged against a spec because errors.py has no per-code docs.
